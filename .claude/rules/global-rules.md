# THE BULLETPROOF METHOD (Mike 8/28 — standing rule, ALL projects, ALL sessions)

Everything we build ships bulletproof: holistically designed, secure, verified,
easy to use, graphically pleasing, and built to last. Before calling ANY new
build, feature, integration, or deliverable done, walk this checklist and fix
what it catches. It applies in every repo on this machine, alongside that
repo's own laws.

## 1. Third-party / vendor / library choices — never cost alone
- Compare AT LEAST two real options before adopting any 3rd-party product,
  service, or dependency. Present the comparison when the choice matters.
- Score on: functionality fit, ease of use (for the actual users AND the
  admin), reliability/track record, security posture, data ownership + exit
  path (can we leave with our data?), longevity (will it exist in 5 years?),
  maintenance burden, and THEN cost. Cheapest is rarely bulletproof;
  most expensive isn't automatically either.
- Prefer boring, proven, widely-adopted tech over novel dependencies. Every
  dependency is a liability we adopt.

## 2. Security — no oversights
- Every new surface gets the attacker's-eye pass: auth on every route,
  least-privilege tokens, no secrets in code/logs/URLs, injection-safe
  queries, same-origin/rate-limit on public endpoints, fail-closed on
  anything that moves money, data, or access.
- New auth/permission surfaces reuse the established gate functions — never
  a fresh ad-hoc check.

## 3. Failure modes — ask "how does this break?" BEFORE shipping
Walk the ways it can go wrong, at minimum:
- **Growth**: files/tables/logs that grow forever (rotate, cap, prune, or
  page them — decide at design time, not when the disk fills).
- **Silent data loss**: is the data ACTUALLY captured? Prove writes with an
  independent read-back, never the code's own success return.
- **Partial failure**: what happens mid-way through — is the operation atomic
  or resumable? Never leave half-applied state.
- **Limits**: rate limits, quotas, payload caps, timeouts, concurrency — hit
  them on purpose in testing before a customer does.
- **Time**: what breaks next month? (cert expiry, token rotation, date
  rollover, stale caches, hardcoded years).
- **The absent author**: can someone else (or a future session) understand,
  administer, and fix it? If the process only lives in one head, it isn't a
  process.

## 4. Whole process, not just code
- Define the FULL lifecycle before building: who uses it, how they find it,
  what happens on each outcome, who administers it, how it's monitored, and
  how it winds down. A feature without its process is half-built.
- Data in = data used: if we capture something, know who consumes it and
  where; if nobody consumes it, don't capture it.

## 5. Ease of use + design
- Easy for the LEAST technical intended user, not the builder. Fewest steps,
  sensible defaults, prefilled data, one obvious next action.
- Graphically pleasing and consistent with the project's design system —
  polish is part of done, not garnish.

## 6. Performance + longevity
- Fast on realistic data sizes (test with production-scale data, not 3 rows).
- Verified end-to-end in the real environment before being called done —
  with proof shown (screenshot, live read-back, delivered artifact).
- Regression-guarded: anything with rules gets a test or validator so the
  next change can't silently break it.

## 7. LOOK at every generated artifact with human eyes (added 8/31 after the
##    un-invoiced Excel shipped machine-verified but human-unreadable)
- Machine-checking that data IS in a file is NOT verification of the file.
  Before shipping any generated document (xlsx, PDF, deck, email, page),
  RENDER it and look at it the way its reader will: screenshot the PDF pages,
  open the workbook layout, view the email HTML. The 8/31 failure: every
  packlist number was programmatically confirmed present, but they sat in a
  2,000-row tab of repeated text nobody could scan — "present" ≠ "findable".
- Ask the reader's question of the artifact: can the least technical intended
  user find the answer they came for in 10 seconds? If key items the
  requester named are in the data, they must be VISIBLE, not just included.
- When source data is known to be incomplete (a permission gap, a class the
  system can't see), say so IN the artifact itself — an absent number with no
  explanation reads as a report bug.

**The bar: would this survive a customer, an attacker, a curious auditor, and
two years of unattended growth? If unsure on any — it isn't done.**

# THE FULL-AUTONOMY & PERFECTION MANDATE (Mike 9/20 — standing rule, ALL projects, ALL sessions)

Mike's words: "If I ask you to do a task you have full permission to execute

- When Mike requests a task, execute it TO COMPLETION without asking
  permission along the way — no "shall I proceed", no mid-task approval
  gates, including the sends/deploys/publishes the task itself requires.

  write to Syteline prod, test-DB-first for DB writes, platform never
  auto-sends cold email, O:\ shares read-only, no passwords typed into

  `/learn` skill into the artifact that should carry it: the responsible

  lives in the conversation is a lesson lost — that is the failure mode.

  alert. Log + notify + remember (state file with last error and streak).

  for 36 h and still isn't installed" catches failure modes nobody coded for.
- Verify the alert fires (send a test) before calling the automation done.
- Windows Authenticode trap: verify signatures only on files with their real
